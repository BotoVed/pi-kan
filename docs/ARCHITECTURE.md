# Архитектура pi-kan (финальная, 2026-10-11)

Статус: **законсервированный контракт**. Изменение любого пункта — через PR, меняющий этот документ.

## 1. Цель

Борда Kan.bn (self-hosted) становится рабочим интерфейсом агента:
очередь задач, прогресс, аудит-трейл и **канал диалога** («чат на доске»).
Человек управляет задачами с телефона (PWA через reverse-proxy), агент —
через MCP/файлы. Никакого другого канала связи система не имеет и не требует.

## 2. Компоненты

```
борда Kan.bn ←── MCP ──── агент (сессия задачи)
     ▲                          ▲   └─ расширение pi-kan (в процессе):
     │                          │      MCP kan · /kan · мандат-гард
     │ REST API                 │ spawn: pi -p --session-id kan-<cardId>
     │ поллинг + замок          │ + payload события
вахтёр-демон (скрипт, БЕЗ LLM) ─┘
                                  артефакты: ~/.kan/tasks/<ID>/
                                  сессии:    pi session-файлы kan-<ID>
```

### 2.1 Вахтёр (watcher)

Демон-скрипт **без LLM**. Цикл: опрос REST API борды → diff состояния →
событие? → замок → спавн сессии. Механические функции:

- **diff→событие** по матрице (§4); состояние предыдущего опроса — кэш, не реестр;
- **замок**: до пробуждения перемещает карточку в «в работе» и пишет коммент
  `wake runId=…` (API-ключ это позволяет — LLM для блокировки не нужен);
- **антиконкурентность**: lockfile по session-id — одна активная сессия на
  карточку; события, пришедшие во время активной сессии, копятся в очередь и
  доставляются следующим пробуждением объединённым payload'ом;
- **стоп-сигнал**: архивация карточки человеком → убить активный процесс сессии;
- **payload-дифф**: в промпт попадает *новость* («коммент: …», «перемещена из X в Y»,
  diff описания), а не пересказ борды — контекст у сессии свой.

### 2.2 Сессия-задача

`pi -p --session-id kan-<cardPublicId> --name "<название задачи>" "<payload>"` —
примитив pi «именованная сессия» даёт ровно нужный контракт
**сессия = задача**: якорь — неизменяемый `kan-<publicId>` (по нему замок,
lockfile, `--session-id`), отображаемое имя — заголовок карточки (обновляется
при пробуждениях; переименование задачи не ломает привязку). В `pi -r` —
читаемый список живых задач «kan-ME-42 · Транскрибация встречи»:

- каждое пробуждение дописывается в ту же сессию: агент видит всю историю
  задачи (ходы, субагентов, находки) в полном контексте;
- процесс живёт один ход и умирает; **живёт контекст, не процесс** — сессия
  «живёт, пока задача не закрыта» в единственном возможном смысле;
- рост контекста — ACP-компакт внутри сессии; критичное не теряется, т.к.
  артефакты лежат файлами (§3);
- интерактивный вход человека: `pi --session-id kan-<ID>` — продолжить диалог
  с клавиатуры, реплики становятся частью контекста задачи;
- закрытая задача — архив: сессия остаётся, `--session-id` вернёт всю кухню.

### 2.3 Агент

Проснувшаяся сессия работает нативными инструментами: MCP борды
(комменты/чек-листы/перемещения/карточки на другие борды), субагенты, bash.
Одно пробуждение = один ход: может включать 5–10 субагентных шагов **без
единого сообщения человеку**; в борду пишутся только вехи, вопросы, результат.

### 2.4 Расширение pi (гарнизон внутри сессии)

**Вахтёр — НЕ расширение**: расширение живёт внутри процесса pi и умирает с
ним; системный демон из него не делается (docs прямо запрещают watchers в
factory). Граница проходит так:

- **watcher** — standalone-демон (systemd unit), см. §2.1;
- **extension** — TypeScript-расширение pi, загружается в КАЖДЫЙ процесс
  сессии (включая `pi -p` — print-режим тоже грузит расширения):
  - `registerMcpServer("kan", …)` — борда поднимается в каждой сессии
    автоматически, без глобального mcp.json;
  - `registerCommand("kan", …)` — `/kan status | attach ME-42 | wake | init`;
  - `on("tool_call")` — **принудительный мандат**: блокирует перемещение/
    удаление карточки в «завершены»/архив (`{ block: true }`) — мандат §5
    из пункта контракта (просьбы) становится кодом харнесса; заодно требует
    агентский тег в `add_card_comment` — антицикл §4 тоже на уровне харнесса;
  - `registerToolRenderer` — комменты/перемещения читаемо в транскрипте.

Расширение не должно иметь UI-зависимостей в print-режиме (`ctx.hasUI` guard).

## 3. Иерархия истины

1. **Артефакты на диске** — `~/.kan/tasks/<ID>/`: выгрузки субагентов,
   транскрипты, черновики. Полная точность, компакту не подлежат; сессия
   ссылается на них путями. Результаты субагентов — **файлами, не пересказом**.
2. **Контекст сессии задачи** — рабочая память (переживает сны/рестарты).
3. **Карточка на борде** — тонкий публичный слой для человека: вехи, вопросы,
   чек-лист, аудит. **НЕ память агента.**

Файлы-вход: **inbox-конвенция** — бинарники/загрузки человек кладёт в
`~/.kan/inbox/`, имя указывает в описании карточки (MCP Kan не имеет
инструментов вложений; REST-вложения — фолбэк, см. §8).

## 4. Матрица событий побудки

| Событие (diff борды) | Вахтёр делает |
|---|---|
| карточка **вошла в «к исполнению»** (создана или перемещена) | замок → пробуждение «выполни» |
| новый коммент **без агентского тега** на карточке любого списка, кроме бэклога/архива | пробуждение с текстом коммента |
| карточка перемещена человеком между списками («завершены»→«в работе» = переоткрыл; «на согласовании»→«в работе» = «продолжай молча») | пробуждение from→to |
| правка описания карточки (diff по хэшу) | пробуждение с diff — канал вводных mid-flight |
| правка чек-листа человеком | слабое пробуждение («пользователь отметил п.N») |
| `dueDate` ≤ сейчас, карточка не в архиве/завершена | напоминательное пробуждение |
| вложение добавлено (если REST допилим) | пробуждение с путём |
| коммент **с агентским тегом** `<!--kan:agent run=…-->` | **ничего** (антицикл) |
| карточка в бэклоге/архиве — внутренние перемещения | **ничего** (но читаем для diff'а выхода) |
| архивация карточки человеком | стоп: убить активную сессию |
| лейблы, состав участников | не события (см. §7 про участников) |
| всё, что касается карточки-конфига `.pi-kan` (правка описания, перемещения) | конфиг-событие: перечитать конфиг, **не будить сессии** (§10) |

**Антицикл.** Один аккаунт / один API-ключ ⇒ автор агентского коммента
неотличим от человеческого. Конвенция: каждый агентский/job-коммент начинается
со скрытого тега `<!--kan:agent run=…-->`; вахтёр такие фильтрует, контракт
пробуждения требует тег ставить.

**Self-wake (долгая работа).** Агент не держит ход живым ради 40-минутного
job'а: запускает фон, заканчивает ход комментом «запущено, ETA». Job по
завершении **сам пишет коммент в карточку** (ключ job'у выдаётся; тег
обязателен — но payload вахтёр строит как «событие job'а», см. WAKE-CONTRACT) →
вахтёр будит сессию дальше. Вечноживущие процессы не нужны: очередь событий —
это и есть планировщик.

## 5. Списки борды и мандат

`бэклог → к исполнению → в работе → на согласовании → завершены` (+ архив).

- **Реестра сессий нет — реестр это борда.** «В работе» = активные задачи.
  Lockfile — только мьютекс писателя сессии, не реестр.
- **Мандат агента: максимум «на согласовании».** В «завершены», архив,
  удаление карточек — только человек. Галлюцинация агента не может уничтожить
  след задачи. Агент, закончивший работу, обязан выставить «на согласовании»
  с итог-комментом и замолчать до решения человека.
- **Каждый человеческий коммент обязан получить ответ** (агентский ответ —
  с тегом). «Право молчать» отвергнуто: чат без ответов не чат.
- Личные борды человека (например «Рабочие задачи») вахтёр **не поллитит** —
  агенты читают/пишут их через MCP как данные (нарезка задач, дедуп).

## 6. Контракт пробуждения

Статичный протокол, который вахтёр инжектит в каждый wake-промпт
(полный текст — [WAKE-CONTRACT.md](WAKE-CONTRACT.md)):

- пробуждение №1: **обязательный первый артефакт — план чек-листом** на
  карточке (3–9 проверяемых пунктов, последний — «итог-коммент + на
  согласование»); только потом исполнение;
- чекать пункты `сразу по факту`, не пачкой (живой прогресс с телефона);
- план не переписывать задним числом — дописывать (аудит-след);
- план кончился, задача не готова → вопрос комментом, не импровизация;
- вопрос = коммент + статус «на согласовании» (агент ждёт хоть неделю — он
  не процесс, это дёшево).

## 7. Участники карточки = «бригада» (конвенция будущего)

- Назначение участника-аккаунта человеком при создании = **директива
  маршрутизации** («это делать вот тому»).
- Агент афиширует подключённых субагентов: пока они не аккаунты — строкой
  «Бригада: vmadmin, researcher» в чек-листе/комменте; при переходе на
  исполнителей-аккаунтов конвенция переезжает в нативных участников без
  смены смысла. Смысл: обзорность, когда субагентов 40.

## 8. Границы и зависимости

- **Единственная внешняя зависимость ядра — Kan.bn по HTTP** (REST вахтёра,
  MCP агента). Ядро = расширение pi: watcher + контракт + файлы задач.
- **Нет Telegram** (и любых пушей) в системе — зависимость; уведомления =
  коммент + «на согласовании». Пуши — внешний мостик снаружи, не часть ядра.
- **Нет завязки на ACP-менеджер** основной сессии: без него просто нет
  компакта, всё остальное работает.
- Разработка — **dogfooding**: карточки на борде будят сессии, которые делают
  само расширение.
- Публикация наружу — reverse-proxy владельца (HTTPS): PWA-установка на
  телефон; вебхуки Kan проходят SSRF-валидатор по доменному имени
  (литеральные приватные IP режутся). **Не фаза 1**: фаза 1 — поллер
  (коммент-событий у Kan нет, retry нет).
- Проверено по исходникам Kan: MCP-инструментов вложений нет; событий
  комментов нет; `create_card` требует обязательный `description` (zod 400).

## 9. Фаза 1 (объём)

1. `watcher` — демон: поллинг (~60 с), матрица событий, замок, lockfile,
   очередь событий, спавн `pi -p --session-id`.
2. Контракт пробуждения — шаблон промпта (роль, мандат, план-чеклист, payload).
3. Конвенции на борде: список «на согласовании», карточка-инструкция,
   inbox-директории, первая dogfooding-задача «сделать расширение pi-kan».

Сознательно не в фазе 1: вебхуки, автозакрытие чек-листов «на глаз»,
PWA/публикация, детектор зависших задач (примитив — чек-лист без движения N
часов → напоминание; после стабилизации контракта).

## 10. Установка (pi-package)

Репозиторий — он же **pi package** (конвенция: `extensions/` + `bin`):

```
pi-kan/
├── package.json        # keywords: ["pi-package"], bin: { "kan-watcher": … }
├── extensions/
│   └── pi-kan.ts       # расширение: MCP kan, /kan, мандат-гард, рендеринг
├── watcher/            # демон: поллер, матрица событий, замок, спавнер
└── docs/
```

Установка:

```bash
pi install git:github.com/BotoVed/pi-kan   # расширение → settings.json pi
kan-watcher install                        # systemd user unit + автозапуск
kan-watcher status
```

### Конфигурация — двухуровневая (борда сама себе конфиг)

**Хост** (`~/.kan/config.json`) — только креды и пути:
`{ url, tokenFile, kanRoot }`. Токен — файл `chmod 600`, никогда в конфигах.
Env-переопределения `KAN_URL`, `KAN_TOKEN_FILE` (dev).

**Борда** — карточка-конфиг **`.pi-kan`**, JSON в **описании** (не в комменте —
единственный идемпотентный канал):

```json
{ "lists": { "backlog": "…", "ready": "…", "inProgress": "…",
             "review": "…", "done": "…" },
  "pollIntervalSec": 60, "maxConcurrent": 2,
  "wake": { "model": null, "thinkingLevel": null },
  "events": { "dueDate": true, "checklistEdits": true },
  "enabled": true, "host": null }
```

`wake.model`/`wake.thinkingLevel` — **необязательные**: `null`/отсутствуют →
флаг не передаётся, действует дефолт pi-конфига хоста. Когда участники
станут аккаунтами-исполнителями, схема расширится маппингом исполнитель→модель
(обратная совместимость: неизвестные ключи — warning, не ошибка).

Правила:
- **нет карточки `.pi-kan` → борда не мониторится** (подписка/отписка борды =
  создание/удаление карточки); `enabled:false` — пауза с сохранением настроек;
- **на борде — только политика; секреты и пути — только на хосте**:
  валидатор конфиг-карточки отвергает ключи `url`/`token*`;
- hot-reload: правка описания `.pi-kan` = событие diff'а → перечитать;
  невалидный/неполный JSON (правка с телефона!) — **last-known-good** из
  локального кэша + коммент-ошибка в ту же `.pi-kan`, вахтёр не падает;
- `.pi-kan` — **не задача**: исключена из матрицы событий (её правка не будит
  сессии), мандат-гард расширяется: агенту move/archive/delete `.pi-kan` — блок;
- идентификация: заголовок `.pi-kan` — конвенция первого поиска; далее вахтёр
  держит publicId конфиг-карточки в локальном кэше (переименование не ломает);
- два хоста с одним токеном: полем `host` (кем мониториться), по умолчанию —
  кто первый встал; не-решение фазы 1 фиксируется явно.

- **Первый запуск** — `/kan init`: проверяет API-ключ, резолвит списки по
  именам в publicId'ы, **создаёт `.pi-kan` с валидным скелетом конфига**
  (борда «подписана»), создаёт `~/.kan/{inbox,tasks}/`. Руками JSON никто не
  пишет — это источник №1 багов «опечатался в publicId».
- **Dev-цикл** — `pi -e ./extensions/pi-kan.ts` (разовая загрузка без
  settings) + `kan-watcher run` (демон на переднем плане, systemd не нужен).
- pi-зависимости (`@earendil-works/pi-coding-agent`, `typebox`) — только в
  `peerDependencies: "*"`, не бандлить (требование packages.md).
- Обновление: `pi update --extensions` (расширение) + `kan-watcher restart`.
